What changed — and what remains a vendor statement?

On 28 October 2026, GitHub announced a shared, dollar-based compute entitlement for standard GitHub Actions runners, Copilot cloud sandboxes and, on eligible plans, larger hosted runners. GitHub says billing for cloud sandboxes begins in November 2026. The connected Copilot cloud experience requires a paid Copilot plan. These are vendor announcements, not results of our independent performance or billing tests.

GitHub's billing documentation adds an important architectural detail: eligible workloads draw from the same included compute value, and no usage type takes priority. Standard runners in public repositories retain separate free-usage treatment.

Why this matters to architects

Teams have often budgeted CI/CD separately from exploratory AI workloads. A shared entitlement creates a new dependency: agent work can consume an allowance also used by build and test automation. That does not prove a pipeline will stop. The outcome depends on the plan, budget settings, and payment configuration. But it does mean shared resource exhaustion belongs in the operational architecture.

Pattern: an agent execution contract

Define an execution contract for every agent workload: accountable owner, repository and data scope, permitted runtime, time and spending limits, stopping policy, usage telemetry, and the response to exhausted budget. Treat this as an architecture decision, not a cosmetic tool preference.

A practical control set:

  1. Separate workload classes. Distinguish release-critical builds and tests from exploratory agents, with clear owners and workload profiles.
  2. Enforce budgets. Verify whether an account configuration actually blocks unplanned spend. An alert alone may not halt a process.
  3. Limit authority. A cloud sandbox is not permission to give an agent broad repository, secret, or deployment access.
  4. Observe the coupling. Record sessions, duration, resource consumption, and stop outcomes; compare them with CI reliability.
  5. Rehearse allowance exhaustion. Test what happens to pipelines, agent sessions, and human recovery when limits are reached.

Anti-pattern: “it is included, so it is effectively unlimited”

An included entitlement is finite. Once depleted, usage may be blocked or billed according to the account's configuration. The organizational failure mode is unclear ownership: no one can explain which workload should yield, who may stop it, or who accepts the consequences.

Questions for the architecture decision

  • Do we know the shared allowance, reset period, and eligible services?
  • Will essential CI continue to function after that allowance is exhausted?
  • Who can start or stop a long-running agent session?
  • How do we separate spending responsibility from the agent's execution privileges and the release pipeline's authority?

Architectural takeaway: the vendor is connecting not only agent interfaces but also the economics of execution. In enterprise architecture, runtime governance and budget governance need a common design.
