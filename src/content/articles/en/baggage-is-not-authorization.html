Fictional educational scenario. A portal handles applications for several organisations. Its frontend sends baggage: tenant.id=alpha downstream to make distributed traces easier to analyse. A team proposes using the same value to select customer records in a reporting service. The identifier arrives with every request. But can the service trust it?

Two kinds of context, two responsibilities

In OpenTelemetry, baggage consists of key–value pairs propagated across processes, often in HTTP headers. It is useful for enriching telemetry. It is not an identity credential or proof of permission to access data. A header value may originate with an untrusted caller. The W3C specification does not assign authorisation semantics to baggage, and OpenTelemetry warns about information disclosure and the absence of built-in integrity protection for baggage values.

traceparent correlates traces; baggage carries additional observability context. Access decisions, by contrast, must be based on trusted identity, permissions and resource context. These are different architectural contracts.

Three design options

  1. Option A — use the baggage tenant as a query filter. This is easy to implement but trusts caller-controlled metadata. A modified header could direct a query to another tenant's records. Reject this option for authorisation.
  2. Option B — keep security context separate; use baggage for diagnostics only. A gateway or authentication service validates credentials, while each service enforcing access derives tenant and permissions from trusted information. Baggage may carry a non-sensitive diagnostic label but cannot decide access. This is the baseline recommendation.
  3. Option C — restrict diagnostic propagation. For systems with stricter confidentiality requirements, disable baggage across selected boundaries or allow only specific keys. This reduces exposure at the cost of some correlation and additional propagator configuration.

A trust-boundary contract

For every service boundary, record the identity source, authorisation enforcement point, permitted telemetry fields, baggage stripping rule for external calls, and verification evidence. Never put tokens, email addresses, account numbers or other sensitive values in baggage. Even an apparently harmless identifier may become identifying when combined with other data.

Five acceptance tests

  1. Send an authenticated request for tenant A with baggage: tenant.id=B. Expected: no access to B's data. A diagnostic label must not alter the authorisation result.
  2. Send a request without authentication but with syntactically valid traceparent and baggage. Expected: protected resources remain inaccessible.
  3. Call a third-party API and capture outgoing headers. Confirm that disallowed baggage and internal information do not cross the boundary; inspect the actual instrumentation configuration.
  4. Inject an oversized or malformed header. Check parsing limits and failure behaviour, and verify that a telemetry error cannot grant additional permissions.
  5. Compare traces, logs and the authorisation decision for one request. Confirm that observability has not become a second source of truth for identity.

What comes from the standards?

W3C defines the baggage format and discusses risks at trust boundaries. OpenTelemetry describes context propagation and cautions against propagating sensitive values. Separating baggage from authorisation context, together with the five tests above, is our architectural recommendation—not a security policy mandated by those specifications.

Architect's question: if a caller changes tenant.id in a header, which component proves that the records they can see remain unchanged?
